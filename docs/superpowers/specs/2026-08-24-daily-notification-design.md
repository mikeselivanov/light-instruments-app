# Уведомление «Имя дня» — дизайн

Дата: 2026-08-24
Статус: реализовано (Tasks 1–5 в `docs/superpowers/plans/2026-08-24-daily-notification.md`). Ниже — дизайн с поправками
по факту реализации; расхождения с первоначальным драфтом (плитка на главном экране, сторонний time picker) отмечены
явно и объяснены в плане.

## Контекст

Приложение «72 Имени Бога» уже вычисляет детерминированное «имя дня»
(`nameOfTheDay()` в [lib/data.ts](../../../lib/data.ts) — одно и то же имя весь
день, меняется в локальную полночь, без `Math.random()`). Фича добавляет
опциональное локальное push-уведомление, которое раз в день напоминает об
этом и по тапу открывает экран с сегодняшним именем.

Уведомление — **строго локальное** (`expo-notifications`, планирование на
устройстве), без сервера и без FCM/Google Play Services. Это важно, потому
что приложение публикуется в том числе в RuStore, где сервисы Google часто
недоступны — удалённый push там был бы ненадёжен.

## Цели

- Пользователь может включить/выключить ежедневное уведомление и выбрать
  время его показа в новом экране «Настройки».
- По умолчанию уведомления выключены (opt-in) — разрешение ОС запрашивается
  только в момент, когда пользователь сам включает тумблер.
- Тап по уведомлению открывает экран с именем дня.
- Тумблер честно отражает реальное состояние разрешения ОС, включая случай,
  когда пользователь отозвал разрешение в системных настройках телефона уже
  после включения тумблера в приложении.

## Не цели

- Не делаем персонализированный текст уведомления (без названия имени в
  тексте) — специально, чтобы не завязываться на пересчёт/переустановку
  уведомления каждый день.
- Не делаем сервер, push-рассылку, аналитику открытий.
- Не проектируем iOS-сборку/публикацию — код пишем платформонезависимо
  (`expo-notifications` работает на обеих платформах одинаково), но сборка и
  публикация под iOS вне рамок этой фичи.

## Архитектура

Новый модуль `lib/notifications.tsx` — React context по образцу
[lib/favorites.tsx](../../../lib/favorites.tsx). Хранит настройки в
AsyncStorage под ключом `notifications:v1`:

```ts
type NotificationSettings = {
  enabled: boolean;
  hour: number;
  minute: number;
};
```

(Реализация не хранит id конкретного запланированного уведомления — вместо отмены «по id» перед
каждой новой постановкой вызывается `cancelAllScheduledNotificationsAsync()`. Так как у приложения
никогда не бывает больше одного активного уведомления, это устраняет риск дублей/утечек при
гонках, не требуя точного отслеживания id.)

Провайдер инкапсулирует всю работу с `expo-notifications`: запрос
разрешения, постановку/отмену повторяющегося локального уведомления.
Уведомление ставится **один раз** через
`scheduleNotificationAsync({ trigger: { hour, minute, repeats: true } })` —
дальше ОС сама повторяет его каждый день. Никаких фоновых задач
(`expo-task-manager`/`expo-background-fetch`) не требуется, так как текст
уведомления фиксированный и не зависит от того, какое именно имя выпало на
сегодня.

## Компоненты и файлы

| Файл | Изменение |
|---|---|
| `lib/notifications.tsx` | **новый** — провайдер + хук `useNotificationSettings()` |
| `app/settings.tsx` | **новый экран** — тумблер, колесо-барабан выбора времени (`TimeWheel`, собственный компонент на `ScrollView`), подсказка о статусе разрешения |
| `app/_layout.tsx` | оборачиваем дерево в `NotificationSettingsProvider`; регистрируем `Notifications.addNotificationResponseReceivedListener` (тёплый тап) и проверяем `getLastNotificationResponse()` при монтировании (холодный старт) |
| `app/index.tsx` | добавляется иконка-шестерёнка рядом с датой → `/settings` (не плитка в сетке — см. ниже) |
| `app.json` | плагин `expo-notifications` (иконка/цвет уведомления для Android) |
| `package.json` | новая зависимость: `expo-notifications` (`@expo/vector-icons` для иконки-шестерёнки уже идёт транзитивно с `expo`) |

**Отличие от первоначального драфта:** вместо плитки «Настройки» в сетке главного экрана и стороннего
`@react-native-community/datetimepicker` реализация использует иконку-шестерёнку рядом с датой и
собственный `TimeWheel`. Причины: (1) плитка визуально «осиротела» под полноширинной плиткой «Все имена» —
пользователь отклонил этот вариант по скриншоту; (2) `@react-native-community/datetimepicker` не имеет
веб-реализации и сломал бы обязательный веб-QA этого проекта. Оба решения согласованы с пользователем
через HTML-мокапы вне дерева приложения — подробности и ссылки на коммиты в
`docs/superpowers/plans/2026-08-24-daily-notification.md`.

## Поток данных

1. Тумблер включён → запрос разрешения ОС (если ещё не выдано) → разрешено:
   `schedule` + сохранить `enabled:true`; отказано: тумблер остаётся
   выключен, показываем инлайн-подсказку.
2. Смена времени (доступна только при включённом тумблере) → отменить все
   запланированные уведомления (`cancelAllScheduledNotificationsAsync`),
   запланировать новое, сохранить.
3. Тумблер выключен → отменить запланированное уведомление, сохранить
   `enabled:false`.
4. При каждом открытии `app/settings.tsx` (`useFocusEffect`) — реальная
   проверка OS-разрешения. Если в хранилище `enabled:true`, а разрешение в
   системе отозвано — тумблер гаснет сам, показываем подсказку «включите
   уведомления в настройках телефона» со ссылкой на системные настройки
   приложения.
5. Текст уведомления фиксированный: «Новое имя дня готово — откройте, чтобы
   узнать».
6. Тап по уведомлению → открывает `app/names/[id]` с именем дня,
   пересчитанным в момент тапа через `nameOfTheDay()` (а не «замороженным»
   на момент показа уведомления). Обрабатываются оба случая: «тёплый» тап
   (приложение уже запущено, `addNotificationResponseReceivedListener`) и
   «холодный старт» (приложение было закрыто, тап его запустил —
   `getLastNotificationResponse()` при монтировании корневого layout).

## Обработка ошибок

- Отказ в разрешении при первом включении → тумблер не включается,
  ненавязчивая инлайн-подсказка (не блокирующий алерт).
- Ошибка `scheduleNotificationAsync` (редкий случай) → тихий catch, тумблер
  откатывается в исходное состояние с подсказкой «не удалось включить,
  попробуйте ещё раз».
- Разрешение отозвано в системных настройках → см. п. 4 потока данных выше.

## Тестирование

- `npx tsc --noEmit` после реализации.
- UI тумблера/time picker'а — визуальная проверка через веб-превью
  (Playwright), как и остальные экраны приложения в этом проекте.
- Реальная доставка локального уведомления **непроверяема в текущем
  окружении разработки** (нет доступа к устройству/эмулятору с работающим ОС
  планировщиком) — требуется ручная проверка на Android-эмуляторе или
  реальном устройстве после EAS-сборки. Это ограничение будет явно указано
  при передаче на реализацию.

## Обязательный гейт перед реализацией и сборкой

**До того как будет написан весь код фичи — и тем более до любой EAS-сборки —
пользователь должен подтвердить визуальный дизайн изменённых и добавленных
экранов**, а именно:

- `app/settings.tsx` (новый экран целиком — расположение тумблера, time
  picker, текста подсказки),
- `app/index.tsx` (точка входа на экран настроек с главного экрана).

Дизайн предоставляется как HTML/Playwright-мокап или скриншот веб-превью
приложения, отправляется пользователю на согласование **до** написания
полной реализации логики (`lib/notifications.tsx`, обработчики разрешений,
интеграция в `app/_layout.tsx`) и **однозначно до** любого
`eas build`. Реализация логики без готового согласованного экрана
не начинается.

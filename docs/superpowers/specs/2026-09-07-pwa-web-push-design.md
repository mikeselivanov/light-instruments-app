# PWA-версия и Web Push — дизайн

Дата: 2026-09-07
Статус: дизайн согласован, план реализации не написан.

## Контекст

Попытки зарегистрировать приложение в Google Play и App Store прекращены. Основным
каналом распространения становится **PWA**, которую пользователь ставит через «Поделиться →
На экран „Домой“». Ссылку владелец раздаёт сам, поисковая выдача не нужна — это прямо
влияет на выбор режима сборки (см. «Решения»).

Приложение уже работает в вебе: текущий QA-процесс — `npm run web` плюс скриншоты
Playwright, и в [app/_layout.tsx](../../../app/_layout.tsx) есть явная защита от
падения `expo-notifications` на вебе. То есть веб — не новая платформа для этого кода,
новая здесь только упаковка (манифест, service worker, установка) и уведомления.

Уведомления — главная сложность. В SDK 54 у `expo-notifications` в документации указано
`platforms: ['android', 'ios']`, веба там нет. И дело не только в Expo: в вебе вообще нет
рабочего API, чтобы запланировать локальное уведомление на «каждый день в 9:00» —
Notification Triggers (`TimestampTrigger`) не доехал до релиза ни в одном браузере.
Единственный способ — **Web Push с сервера**, то есть VAPID, хранение подписок и крон.
Это превращает задачу из «выложить статику» в «статика плюс сервис».

Инфраструктура: своя VPS, домен `smixa.ru`, на портах 80/443 уже работает другой сайт
под **nginx напрямую** (systemd, не Docker). Конфликта нет — name-based virtual hosting
плюс TLS SNI позволяют обслуживать оба домена одним nginx на тех же портах.

## Цели

- Приложение доступно по `https://72.smixa.ru`, ставится на домашний экран на iOS и Android.
- Полная работа офлайн: весь контент (72 имени) уже в бандле, кешируется целиком.
- Ежедневное уведомление об имени дня работает в PWA — паритет с нативной версией.
- Первый экран открывается быстро: бюджет шрифтов сокращён с 1.76 МБ.
- Нативные сборки (RuStore APK) продолжают собираться без изменений.

## Не цели

- Поисковая выдача и SEO. Владелец делится ссылкой сам, поэтому режим `static` с 72
  пререндеренными страницами сознательно отклонён в пользу более простого SPA.
- React Server Components и API-роуты Expo (`output: "server"`) — потребовали бы Node
  под самим фронтом.
- Аккаунты и синхронизация избранного между устройствами. Как и сейчас — `localStorage`
  в пределах origin.
- Аналитика, Badging API.

## Решения

| Решение | Выбор | Почему |
|---|---|---|
| Режим сборки веба | `web.output: "single"` (SPA) | SEO не нужен — ссылка раздаётся вручную. Экономит `+html.tsx`, `generateStaticParams` и переделку гейта на шрифтах в корневом лейауте. |
| Уведомления | Web Push сразу, не отдельной фазой | Решение владельца: паритет с нативом важнее скорости первой выкатки. |
| Service worker | Workbox `injectManifest` | Нужны свои обработчики `push`/`notificationclick`; `generateSW` кастомный код не принимает. |
| Хранилище подписок | `node:sqlite` | Встроен в Node, никаких нативных сборок на VPS. **Требует Node ≥ 22** (в Node 24+ стабилен). |
| Шрифты | Подрезка + woff2 через `subset-font` | `pyftsubset` требует Python, которого в цепочке нет; `subset-font@2.7.0` использует wasm-сборку harfbuzz. |
| Деплой | Локальная сборка + `rsync` по SSH | Минимум движущихся частей; Metro на маленькой VPS может упереться в память. |

## Архитектура

```
DNS: 72.smixa.ru  A → IP VPS

nginx (существующий, 80/443, +1 server-блок, +1 сертификат certbot)
 │
 ├─ location /      → root /var/www/72.smixa.ru
 │                    try_files $uri /index.html        ← SPA-фоллбэк
 │                    /sw.js  → Cache-Control: no-cache ← иначе обновления залипают
 │                    /assets/* → immutable, 1 год      ← имена файлов хешированы
 │
 └─ location /api/  → proxy_pass http://127.0.0.1:8787
                      limit_req
                            │
                            └─ systemd: 72names-push.service
                               Node + web-push + node:sqlite
                               тик раз в 60 с
                               /var/lib/72names/subs.db
                               /etc/72names/env   (VAPID_PRIVATE_KEY, 0600)
```

`/api/` живёт на том же поддомене, а не отдельным хостом — один origin, поэтому CORS и
preflight-запросы не нужны вовсе.

## Поток данных

### Подписка

```
Пользователь жмёт тумблер в настройках
  → Notification.requestPermission()          (обязательно из жеста — требование iOS)
  → navigator.serviceWorker.ready
  → registration.pushManager.subscribe({ userVisibleOnly: true,
                                          applicationServerKey: VAPID_PUBLIC })
  → POST /api/subscribe { endpoint, keys, hour, minute, tz }
  → сервер: upsert по endpoint
```

`tz` — IANA-зона из `Intl.DateTimeFormat().resolvedOptions().timeZone`.
Публичный VAPID-ключ попадает в бандл через `EXPO_PUBLIC_VAPID_PUBLIC_KEY` — он публичный
по определению. Приватный не покидает `/etc/72names/env`.

### Отправка

```
Тик раз в 60 с
  → для каждой подписки: местное время в её tz
  → если местное время УЖЕ НАСТУПИЛО ИЛИ ПРОШЛО и last_sent_day ≠ сегодня (местный)
      → имя дня = floor(Date.now()/86_400_000) % 72   (та же формула, что в lib/data.ts)
      → web-push send { title, body: title имени, url: "/names/<id>" }
      → last_sent_day = сегодня
  → ответ 404/410 → удалить подписку
```

Условие отправки намеренно сформулировано как «уже наступило», а не «ровно равно».
Строгое равенство теряет уведомление насмерть, если процесс перезапустили в эту самую
минуту или тик подтормозил; формулировка «уже наступило» самовосстанавливается —
отправит с опозданием, но отправит.

Текст уведомления считает сам сервер, читая **тот же** `assets/data/names.ru.json`
(деплой-скрипт кладёт его рядом с сервисом). Источник правды остаётся один. Побочный
выигрыш: в уведомлении можно показать само имя, а не безликое «новое имя дня готово».

Формула `floor(getTime()/86_400_000)` считает дни по UTC, а не по местной полуночи
(вопреки комментарию в [lib/data.ts](../../../lib/data.ts) — расхождение существующее и в
рамках этой задачи не исправляется). Клиент и сервер используют одну формулу, поэтому
между собой они согласованы всегда.

### Тап по уведомлению

```
notificationclick в SW
  → есть открытый клиент приложения? → focus() + navigate(data.url)
  → иначе                            → clients.openWindow(data.url)
```

## Схема БД

```sql
CREATE TABLE IF NOT EXISTS subscriptions (
  endpoint      TEXT PRIMARY KEY,
  p256dh        TEXT NOT NULL,
  auth          TEXT NOT NULL,
  hour          INTEGER NOT NULL,
  minute        INTEGER NOT NULL,
  tz            TEXT NOT NULL,
  last_sent_day TEXT,             -- локальная дата 'YYYY-MM-DD' последней отправки
  created_at    INTEGER NOT NULL
);
```

Персональных данных не хранится: ни аккаунтов, ни почты, ни имени. Только endpoint push-сервиса
(в нём вендорный токен браузера), ключи шифрования, выбранное время и таймзона.

## Контракт контекста уведомлений

`lib/notifications.web.tsx` подхватывается Metro автоматически вместо `.tsx` при сборке
под web, поэтому [app/settings.tsx](../../../app/settings.tsx) продолжает работать почти
без правок.

| Поле | Натив (сейчас) | Веб (новое) |
|---|---|---|
| `setEnabled(true)` | permission + локальный график | `requestPermission` → `pushManager.subscribe` → `POST /api/subscribe` |
| `setEnabled(false)` | `cancelAllScheduled` | `POST /api/unsubscribe` + локальный `subscription.unsubscribe()` |
| `setTime(h, m)` | перепланировать | `POST /api/subscribe` (upsert по endpoint) |
| `osPermissionDenied` | статус permission | `Notification.permission === 'denied'` |
| `scheduleError` | ошибка планирования | сеть или подписка не удались |
| `installRequired` | всегда `false` | iOS, push недоступен, пока не добавлено на домашний экран |

`installRequired` — единственная правка контракта, и она вынужденная: на iOS подписаться
из вкладки Safari нельзя в принципе, и пользователю надо это объяснить, а не показывать
«ошибка, попробуйте ещё раз».

## Установка

- **Android/Chrome**: перехватываем `beforeinstallprompt`, подавляем родной баннер и
  показываем свою кнопку — штатный баннер Chrome легко пропустить.
- **iOS**: события `beforeinstallprompt` не существует. Показываем короткую инструкцию
  «Поделиться → На экран „Домой“», и только если ещё не в standalone
  (`navigator.standalone !== true`).
- Оба варианта не показываются повторно после установки или явного отказа (флаг в
  `localStorage`).

Требования iOS, от которых это зависит (iOS/iPadOS 16.4+, [WebKit blog](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)):
Web Push доступен **только** веб-приложениям, добавленным на домашний экран; запрос
разрешения обязан идти из прямого действия пользователя; манифест должен объявлять
`display: standalone` или `fullscreen`.

## Шрифты

Пять `.ttf` весят **1.76 МБ**, а в [app/_layout.tsx](../../../app/_layout.tsx) стоит
`if (!fontsLoaded) return null`. То есть при первом заходе виден пустой экран, пока не
скачается всё — ровно в момент, когда человек открыл присланную ссылку и решает,
оставлять ли приложение.

### Мёртвый шрифт

`PTSerif-Regular.ttf` (**350.6 КБ**) загружается в `_layout.tsx`, но в интерфейсе не
используется **ни разу**: токен `displayRu` объявлен в
[lib/theme.ts](../../../lib/theme.ts), однако ни один `fontFamily` в `app/` и
`components/` на него не ссылается (используются только `body`, `displayRuBold`,
`bodyBold`, `displayHebrew`).

Убираем и файл из загрузки, и токен `displayRu`. Токен, указывающий на незагруженный
шрифт, — ловушка: он молча отваливается на системный, и заметить это трудно. Выигрыш
достаётся **и нативу тоже** — минус 350 КБ из APK и из времени старта, бесплатно.

### Подрезка

`scripts/build-fonts.mjs` подрезает оставшиеся четыре шрифта через `subset-font` и
упаковывает в woff2:

- PT Sans (Regular, Bold), PT Serif Bold — кириллица + латиница + пунктуация. Сейчас
  тащат ещё греческий и расширенную латиницу, которые не используются.
- Ashurit — только иврит, диапазон `U+0590–U+05FF`.

Расчёт бюджета (woff2 обычно даёт 40–50 % от TTF, подрезка — ещё сверху):

| Шрифт | Сейчас | Ожидаемо |
|---|---|---|
| PTSans-Regular | 432.6 КБ | ~110–140 КБ |
| PTSans-Bold | 459.2 КБ | ~120–150 КБ |
| PTSerif-Bold | 332.0 КБ | ~90–110 КБ |
| Ashurit | 186.2 КБ | ~50–70 КБ |
| ~~PTSerif-Regular~~ | ~~350.6 КБ~~ | **0 — удалён** |
| **Итого** | **1.76 МБ** | **~370–470 КБ** |

Гейт `fontsLoaded` при этом **сохраняется**: типографика — часть замысла, и подмена
шрифта на лету выглядела бы хуже, чем чуть более долгий, но целостный первый экран.
После первого захода всё мгновенно — SW уже закешировал.

Критерий приёмки: веб-набор шрифтов **≤ 500 КБ** суммарно. Если не уложились — решение
пересматривается (первый кандидат на выброс — `PTSans-Bold`, всего 2 использования).

### Риск, требующий проверки в плане

Веб-реализация `expo-font` подключает шрифты через FontFace API. Формат woff2 браузеры
поддерживают повсеместно, но **не проверено, не завязан ли загрузчик Expo на расширение
файла**. План должен содержать раннюю проверку «шрифт в woff2 реально отрисовался в
браузере» — до того, как на эту схему завяжется весь остальной шрифтовой шаг. Запасной
вариант, если загрузчик капризничает: оставить `.ttf` и ограничиться подрезкой без смены
контейнера (выигрыш меньше, но бюджет всё равно сокращается примерно вдвое).

## Service worker

Три обязанности:

1. **Офлайн** — `precacheAndRoute(self.__WB_MANIFEST)` плюс `navigateFallback: '/index.html'`.
   Весь контент в бандле, поэтому офлайн получается полный, а не частичный.
2. **`push`** — `showNotification(...)` с `data.url = '/names/<id>'` из payload.
3. **`notificationclick`** — фокус существующей вкладки либо `clients.openWindow`.

Обновления: `skipWaiting()` + `clientsClaim()`, чтобы свежая версия применялась на
следующем открытии. Документация Expo отдельно предупреждает про залипающий кеш —
это защита от него, вместе с `Cache-Control: no-cache` на `/sw.js` в nginx.

## Обработка ошибок

Приложение остаётся полностью работоспособным при любом отказе уведомлений — это не
критический путь:

| Отказ | Поведение |
|---|---|
| SW не зарегистрировался | Приложение работает, офлайна нет, тумблер уведомлений отдаёт `scheduleError`. |
| `Notification.permission === 'denied'` | Подсказка про настройки браузера/системы. Без `Linking.openSettings()` — в вебе такого API нет. |
| iOS во вкладке Safari | `installRequired`, инструкция по установке вместо ошибки. |
| `/api/` недоступен | `scheduleError`, тумблер откатывается в выключенное состояние. |
| Сервис лежит | Уведомления не приходят, всё остальное работает. |
| Подписка протухла | Сервер удаляет строку по 404/410 от push-сервиса. |

## Безопасность

`/api/subscribe` открыт всему интернету, поэтому:

- `limit_req` в nginx на `/api/`;
- потолок на общее число строк в таблице;
- валидация хоста endpoint по списку известных push-сервисов
  (`*.googleapis.com`, `*.push.apple.com`, `*.mozilla.com`);
- `/etc/72names/env` с приватным VAPID-ключом — права `0600`, сервис работает от
  непривилегированного пользователя;
- секреты не попадают в git: `.env` в `.gitignore`, на сервере ключи задаются вручную один раз.

## Тестирование

`localhost` считается secure context, поэтому service worker и подписка на push проверяются
локально без сертификатов:

1. `npm run build:web` → `npx expo serve`, сервис поднят рядом на 8787.
2. `node server/send.mjs --force <endpoint>` — отправить пуш немедленно, не дожидаясь
   назначенной минуты. Без этого отладка превращается в сидение у часов.
3. Проверка офлайна: DevTools → Network → Offline, полный обход экранов.
4. Проверка тика: подписка на время «через минуту», ожидание реальной доставки.
5. `npx tsc --noEmit` — проект собирается со `strict: true`.
6. Регресс натива: `npm run android`, тумблер уведомлений и время по-прежнему работают
   через `expo-notifications`.

**iOS проверяется только на реальном домене после деплоя.** Состояние «добавлено на
домашний экран» локально не эмулируется, поэтому финальный прогон — ручной, на телефоне
владельца: установка, выдача разрешения, приход уведомления, тап и переход на имя дня.

По конвенции проекта (см. спеку от 2026-08-24) **новый и изменённый UI согласуется
до написания полной реализации**. Под гейт попадают:

- `components/InstallBanner.tsx` — целиком новый элемент, ничего похожего ещё не видели;
- новые подсказки в [app/settings.tsx](../../../app/settings.tsx): `installRequired` и
  веб-вариант `osPermissionDenied`.

Согласование — один HTML/Playwright-мокап, отправляется владельцу **до** написания
`lib/notifications.web.tsx`, серверной части и любого деплоя. Итерации по мокапу не
нужны: после выбора варианта сразу идёт реализация.

Отдельный гейт инфраструктуры: **DNS-запись `72.smixa.ru` и сертификат Let's Encrypt
должны существовать до первого деплоя.** Без HTTPS не работают ни service worker, ни
установка, ни push, и самоподписанный сертификат не подойдёт.

## Область следующего шага (implementation plan)

План создаётся отдельно через `writing-plans` и должен явно содержать:

- блокирующий чекпоинт «мокап InstallBanner и подсказок настроек → согласование»
  перед реализацией логики;
- **раннюю** проверку, что woff2 отрисовывается через `expo-font` на вебе, — до того как
  на эту схему завяжется остальной шрифтовой шаг;
- измерение итогового бюджета шрифтов (≤ 500 КБ) как отдельный проверяемый критерий,
  с фактическими цифрами в отчёте, а не «стало меньше»;
- шаг проверки, что нативная сборка не сломана, до деплоя веба;
- ручной прогон на iOS-устройстве как финальный шаг приёмки.
